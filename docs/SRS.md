# سند نیازمندی‌های نرم‌افزار (SRS)
## Software Requirements Specification

**پروژه:** سامانه هوشمند مدیریت آلارم و پایش سلامت لایه‌های حفاظتی ایمنی فرآیند (BHAM)
**مشتری:** شرکت پتروشیمی غدیر
**توسعه‌دهنده:** شرکت پتروپالاتوس
**نسخه سند:** 1.0.0
**استاندارد مرجع:** IEEE 830 + ISO/IEC/IEEE 29148

---

## ۱. مقدمه

### ۱.۱ هدف سند
این سند نیازمندی‌های فنی و عملکردی نرم‌افزار BHAM را برای توسعه‌دهندگان، آزمایش‌کنندگان، و کاربران فنی تعریف می‌کند. این سند مبنای طراحی، پیاده‌سازی، آزمایش و پذیرش محصول است.

### ۱.۲ محدوده محصول
نرم‌افزار BHAM یک پلتفرم تحلیلی مبتنی بر هوش مصنوعی برای پایش ایمنی فرآیند است که شامل چهار ماژول AI، یک ماژول تشخیص خطای فرآیند، یک API سرویس، و یک داشبورد وب است.

### ۱.۳ تعاریف و مخفف‌ها
| اصطلاح | تعریف |
|---|---|
| BHAM | Barrier Health & Alarm Manager |
| DCS | Distributed Control System |
| SIS | Safety Instrumented System |
| ESD | Emergency Shutdown |
| BPCS | Basic Process Control System |

| RBI | Risk-Based Inspection |

| IEC 61511 | کارکرد ایمنی SIS برای فرآیندهای صنعتی |

### ۱.۴ مراجع
- IEC 61511 Functional Safety: SIS for the Process Industry Sector
- IEC 61508 Functional Safety of E/E/PE Systems
- ISA 18.2 Management of Alarm Systems for the Process Industries
- EEMUA 191 Alarm Systems — A Guide to Design, Management and Procurement
- IEEE 830 / ISO/IEC/IEEE 29148 Software Requirements Specification
- Rieth et al. (2017) — Additional TEP Simulation Data for Anomaly Detection

## ۲. توصیف کلی

### ۲.۱ نمای محصول
BHAM یک سرویس پایتون است که از طریق REST API با کاربران و سیستم‌های جانبی تعامل دارد و خروجی‌ها را در داشبورد وب نمایش می‌دهد. چهار ماژول AI به‌صورت مستقل آموزش می‌بینند اما از طریق API یکپارچه عرضه می‌شوند.

### ۲.۲ کلاس‌های کاربری
| کاربر | سطح دسترسی | وظیفه |
|---|---|---|
| اپراتور واحد | فقط مشاهده | دیدن آلارم‌های اولویت‌دار و وضعیت لایه‌ها |
| کارشناس ایمنی فرآیند | مشاهده + تحلیل | تحلیل ریشه علت، گزارش‌گیری |
| مدیر HSE | مشاهده + پیکربندی | تنظیم آستانه‌ها، مشاهده KPI کلان |
| مهندس داده | توسعه + نگهداری | آموزش مجدد مدل، پایش سلامت سرویس |

### ۲.۳ محدودیات طراحی
- زبان توسعه: پایتون ۳.۱۰+ برای منطق و مدل‌ها، HTML/CSS/JS برای داشبورد.
- هیچ وابستگی به سرویس ابری خارجی نداشته باشد (قابل استقرار On-Premise).
- مدل‌ها باید قابل ذخیره و بارگذاری مجدد باشند (joblib/pickle).
- محتوای گزارش‌ها به زبان فارسی با پشتیبانی کامل RTL و فونت فارسی است.

### ۲.۴ وابستگی‌ها
کتابخانه‌های اصلی: numpy, pandas, scikit-learn, scipy, statsmodels, xgboost, lightgbm, fastapi, uvicorn, joblib, pydantic.

## ۳. نیازمندی‌های عملکردی

هر نیازمندی با شناسه FR-x-y مشخص می‌شود. x شماره ماژول و y شماره ترتیبی است.

### ۳.۱ ماژول ۱: تحلیل و اولویت‌بندی آلارم
- **FR-1-1:** سامانه باید لاگ آلارم را در قالب CSV با حداقل ستون‌های timestamp, tag, priority, status دریافت کند.
- **FR-1-2:** سامانه باید شاخص‌های EEMUA 191 را محاسبه کند: نرخ آلارم در ساعت، تگ‌های چترینگ، آلارم‌های ثابت‌مانده، رویدادهای طوفان آلارم، سهم ۱۰ تگ پرتکرار.
- **FR-1-3:** سامانه باید با DBSCAN خوشه‌های زمانی آلارم را شناسایی کند و برای هر خوشه: تگ ریشه محتمل، امتیاز اولویت، و پرچم طوفان را گزارش دهد.
- **FR-1-4:** سامانه باید با Isolation Forest آلارم‌های ناهنجار را با امتیاز ناهنجاری شناسایی کند.
- **FR-1-5:** سامانه باید برای ۲۰ تگ پرتکرار پیشنهاد بازنگری حد بالا/پایین بر اساس تحلیل آماری (μ ± 3σ) ارائه دهد.
- **FR-1-6:** زمان پاسخ تحلیل برای ۱۰٬۰۰۰ آلارم باید کمتر از ۵ ثانیه باشد.

### ۳.۲ ماژول ۲: پایش سلامت لایه‌های حفاظتی
- **FR-2-1:** سامانه باید وضعیت ۵ لایه حفاظتی (BPCS, SIS, ESD, Relief, Procedural) را برای هر واحد نگهداری کند.
- **FR-2-2:** سامانه باید شاخص سلامت هر لایه را با فرمول تجمیع وزنی (base × decay × test_factor) با جریمه بایپس محاسبه کند.
- **FR-2-3:** سامانه باید PFD (احتمال خرابی هنگام تقاضا) را با مدل Poisson تقریب بزند.
- **FR-2-4:** سامانه باید رویدادهای تجمع ضعف (≥ ۲ لایه همزمان ضعیف یا بایپس) را به‌عنوان پرخطر گزارش دهد.
- **FR-2-5:** سامانه باید ریسک کل واحد را به‌عنوان میانگین وزنی (۱ - سلامت) گزارش دهد.
- **FR-2-6:** سامانه باید پیشنهاد برنامه بازرسی مبتنی بر ریسک (RBI) با اولویت‌بندی ارائه دهد.
- **FR-2-7:** توصیه متنی برای هر لایه باید بر اساس وضعیت (بایپس، تأخیر تست، نرخ تست ناموفق، سلامت) تولید شود.

### ۳.۳ ماژول ۳: پیش‌بینی توالی منجر به توقف
- **FR-3-1:** سامانه باید توالی رویدادها را با کاراکتر `|` جدا شده دریافت کند.
- **FR-3-2:** سامانه باید با TF-IDF + Random Forest احتمال توقف/ناایمن را پیش‌بینی کند.
- **FR-3-3:** سامانه باید با زنجیره مارکوف مرتبه ۲ رویداد بعدی محتمل و احتمال آن را پیش‌بینی کند.
- **FR-3-4:** سامانه باید خروجی شامل: شناسه توالی، احتمال توقف، رویداد بعدی، زمان پیش‌گویی، سطح ریسک باشد.
- **FR-3-5:** سامانه باید ۱۰ ویژگی برتر از نظر اهمیت را گزارش دهد.
- **FR-3-6:** دقت (recall کلاس مثبت) باید ≥ ۰.۹۰ روی داده آزمون باشد (تأیید شده با AUC ≥ ۰.۹۷).

### ۳.۴ ماژول ۴: ریسک پویا و بهینه‌سازی تست
- **FR-4-1:** سامانه باید سیگنال‌های عملیاتی (دما، فشار، جریان، لرزش، ساعت کارکرد) را دریافت کند.
- **FR-4-2:** سامانه باید با XGBoost احتمال خرابی را پیش‌بینی کند.
- **FR-4-3:** سامانه باید با مدل Weibull AFT، MTBF (میانگین زمان تا خرابی) را برآورد کند.
- **FR-4-4:** سامانه باید ریسک پویا = P × (1 + stress factor) را محاسبه کند و آن را به ۴ سطح Low/Medium/High/Critical طبقه‌بندی کند.
- **FR-4-5:** سامانه باید برنامه تست و بازرسی بهینه با فاصله پیشنهادی (۳۰ تا ۲× فاصله پایه) و اولویت ارائه دهد.
- **FR-4-6:** سامانه باید توصیه عملیاتی متناسب با سطح ریسک تولید کند.

### ۳.۵ ماژول ۵: تشخیص خطای فرآیند (TEP)
- **FR-5-1:** سامانه باید داده فرآیند با ۵۲ متغیر را برای تشخیص خطا بپذیرد.
- **FR-5-2:** سامانه باید با PCA (۱۵ مؤلفه) و آماره T² و SPE ناهنجاری را تشخیص دهد.
- **FR-5-3:** سامانه باید با Random Forest نوع خطا را طبقه‌بندی کند.
- **FR-5-4:** سامانه باید FDR (نرخ تشخیص) و FAR (نرخ هشدار کاذب) را گزارش دهد.
- **FR-5-5:** سامانه باید روی داده آزمون TEP با میانگین FDR ≥ ۰.۳۰ و FAR ≤ ۰.۰۵ کار کند.

### ۳.۶ API و داشبورد
- **FR-6-1:** سامانه باید یک REST API باFastAPI ارائه دهد با endpointهای:
  - `GET /api/v1/health` — بررسی سلامت سرویس
  - `POST /api/v1/alarms/analyze` — تحلیل آلارم
  - `POST /api/v1/barriers/health` — محاسبه سلامت لایه‌ها
  - `POST /api/v1/sequences/predict` — پیش‌بینی توالی
  - `POST /api/v1/risk/estimate` — برآورد ریسک پویا
  - `POST /api/v1/tep/detect` — تشخیص خطای فرآیند
  - `GET /api/v1/metrics/summary` — خلاصه KPIها
- **FR-6-2:** تمام پاسخ‌ها باید JSON با schema یکسان (status, data, errors) باشند.
- **FR-6-3:** داشبورد باید KPIهای کلان، نمودار توزیع ریسک، نمودار سلامت لایه‌ها، و فهرست آلارم‌های اولویت‌دار را نمایش دهد.
- **FR-6-4:** داشبورد باید واکنش‌گرا (responsive) و در تلفن، تبلت و دسکتاپ قابل استفاده باشد.
- **FR-6-5:** داشبورد باید RTL و فونت فارسی داشته باشد.

## ۴. نیازمندی‌های غیرعملکردی

### ۴.۱ کارایی (Performance)
- **NFR-P1:** تحلیل ۱۰٬۰۰۰ آلارم در کمتر از ۵ ثانیه.
- **NFR-P2:** پیش‌بینی توالی ۱۰۰ توالی در کمتر از ۲ ثانیه.
- **NFR-P3:** برآورد ریسک ۱٬۰۰۰ نمونه در کمتر از ۳ ثانیه.
- **NFR-P4:** زمان راه‌اندازی سرویس کمتر از ۱۰ ثانیه.

### ۴.۲ قابلیت اطمینان (Reliability)
- **NFR-R1:** دسترس‌پرسی ۹۹.۵٪ در ساعات اداری.
- **NFR-R2:** مدل‌ها باید قابل ذخیره و بارگذاری باشند (joblib/pickle).
- **NFR-R3:** در صورت خطای یک ماژول، سایر ماژول‌ها باید به کار خود ادامه دهند (fault isolation).

### ۴.۳ امنیت (Security)
- **NFR-S1:** تمام endpointهای API باید از طریق توکن احراز هویت شوند (در فاز پایلوت).
- **NFR-S2:** داده‌های حساس باید در حالت استقرار رمزگذاری شوند.
- **NFR-S3:** لاگ دسترسی‌ها باید نگهداری شود.
- **NFR-S4:** انطباق با IEC 62443 (امنیت سیستم‌های صنعتی).

### ۴.۴ نگهداری‌پذیری (Maintainability)
- **NFR-M1:** پوشش تست واحد ≥ ۸۰٪ (تأیید شده: ۹۴٪).
- **NFR-M2:** تمام کد باید مستندسازی شده باشد (docstring فارسی).
- **NFR-M3:** معماری ماژولار؛ افزودن ماژول جدید بدون تغییر سایر ماژول‌ها.
- **NFR-M4:** همه اسکریپت‌ها باید قابل بازتولید باشند (seed ثابت، نسخه‌گذاری وابستگی).

### ۴.۵ حمل‌پذیری (Portability)
- **NFR-PO1:** قابل اجرا روی Linux Ubuntu 22.04+ و CentOS 8+.
- **NFR-PO2:** قابل استقرار در Docker.
- **NFR-PO3:** پایتون ۳.۱۰ تا ۳.۱۲ پشتیبانی می‌شود.

### ۴.۶ مقیاس‌پذیری (Scalability)
- **NFR-SC1:** پشتیبانی از ۱۰۰ کاربر همزمان در داشبورد.
- **NFR-SC2:** پشتیبانی از ۱ میلیون رکورد آلارم در هر تحلیل.

### ۴.۷ کارپذیری (Usability)
- **NFR-U1:** داشبورد باید در کمتر از ۳ کلیک به هر KPI اصلی برسد.
- **NFR-U2:** طراحی واکنش‌گرا برای ۳۷۵px تا ۱۹۲۰px.
- **NFR-U3:** رنگ‌بندی معنادار برای سطح ریسک (سبز/زرد/نارنجی/قرمز).

### ۴.۸ قابلیت ردیابی و حسابرسی (Auditability)
- **NFR-A1:** لاگ تمام درخواست‌ها با timestamp و کاربر.
- **NFR-A2:** ذخیره تاریخچه نسخه‌های مدل.
- **NFR-A3:** گزارش پوشش تست قابل تولید باشد (`pytest --cov`).

## ۵. نیازمندی‌های داده

### ۵.۱ داده ورودی
- لاگ آلارم: CSV با ستون‌های timestamp, tag, priority, status, value, setpoint, ack_delay_sec, clear_delay_sec, operator.
- وضعیت لایه‌ها: timestamp, unit, layer, health_score, bypass_active, last_test_result, days_since_test, sensor_drift, response_delay_s.
- توالی رخدادها: sequence_id, events (با جداکننده `|`), shutdown_risk.
- سیگنال‌های فرآیند: timestamp, unit, temperature_c, pressure_bar, flow_kg_h, vibration_mm_s, operating_hours, failure.

### ۵.۲ داده خروجی
- گزارش JSON هر ماژول در `reports/`.
- مدل‌های آموزش‌دیده در `models/`.
- داشبورد زنده.

### ۵.۳ ذخیره‌سازی
- داده خام: `data/raw/` و `data/real/raw_tep/`.
- داده پردازش‌شده: `data/processed/` و `data/real/processed/`.
- مدل‌ها: `models/` با فرمت joblib.
- گزارش‌ها: `reports/` با فرمت JSON + HTML coverage.

## ۶. معماری سیستم

### ۶.۱ لایه‌ها
1. **لایه داده:** خواندن CSV، DDS، لاگ DCS/SIS.
2. **لایه پردازش:** نرمال‌سازی، استخراج ویژگی، تبدیل زمان.
3. **لایه مدل:** چهار ماژول AI + تشخیص خطای TEP.
4. **لایه سرویس:** FastAPI REST API.
5. **لایه نمایش:** داشبورد HTML تک‌فایلی.

### ۶.۲ جریان داده
```
DCS/SIS → log files → preprocess → models (4 + TEP) → API → Dashboard
                              ↓
                         reports/ + models/
```
